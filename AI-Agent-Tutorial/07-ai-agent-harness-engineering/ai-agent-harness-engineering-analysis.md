## 1. 什么是 Harness Engineering

### 1.1 定义

**Harness Engineering（线束工程 / 脚手架工程）** 是围绕 AI 模型构建系统、工具、约束和反馈回路，使其在生产环境中可靠运行的工程学科。

> **Agent = Model + Harness**
>
> 模型提供智能，Harness 提供可靠性。

Harness 包含围绕模型的一切基础设施：Agent 循环、工具注册与执行、权限控制、多 Agent 协调、错误恢复、会话管理、验证闭环和可观测性。

### 1.2 Harness Engineering 的定位

```
┌──────────────────────────────────────────────────────────────────┐
│                    AI Agent 工程三大支柱                          │
│                                                                  │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────────┐   │
│  │ Prompt        │  │ Context      │  │ Harness              │   │
│  │ Engineering   │  │ Engineering  │  │ Engineering          │   │
│  │              │  │              │  │                      │   │
│  │ 告诉模型      │  │ 控制模型      │  │ 围绕模型构建           │   │
│  │ "怎么做"      │  │ "看到什么"    │  │ "执行基础设施"         │   │
│  │              │  │              │  │                      │   │
```

### 1.3 为什么 Harness Engineering 至关重要

- **LangChain 实证**：仅改进 Harness（不换模型），编码 Agent 准确率从 52.8% 提升到 66.5%（提升 26%）
- **OpenAI 实证**：用 Codex Agent + Harness 构建了超过 100 万行代码的内部产品，零人工编写代码
- **核心洞察**：模型能力是必要条件，但 Harness 质量决定了 Agent 在生产环境中的可靠性上限

### 1.4 Harness 与传统软件架构的区别

| 维度 | 传统软件 | Agent Harness |
|------|---------|--------------|
| **执行流程** | 确定性，代码控制 | 非确定性，模型决策 |
| **错误模式** | 崩溃、异常 | 幻觉、循环、偏离目标 |
| **状态管理** | 数据库/内存 | 上下文窗口 + 外部记忆 |
| **权限模型** | RBAC/ACL | 工具级分级权限 + 人类审批 |
| **测试方法** | 单元/集成/E2E | 随机性评估 + 基准测试 |
| **可观测性** | 日志/指标/追踪 | + 上下文组成追踪 + 工具调用链 |

## 3. 各 Agent Harness 架构详细分析

### 3.1 Claude Code

#### Harness 架构总览

Claude Code 拥有业界最成熟的 Agent Harness，采用 **流式 Agentic Loop + 12 个生命周期钩子 + 5 级权限** 的架构：

```
┌─────────────────────────────────────────────────────────────────┐
│                  Claude Code Harness 全景图                      │
│                                                                 │
│  ┌─ Agent 循环（流式 ReAct Loop）───────────────────────────┐   │
│  │                                                           │   │
│  │   ┌──────┐    ┌────────────────┐    ┌──────────────┐     │   │
│  │   │ 接收  │ →  │ 评估+生成响应   │ →  │ 执行工具     │     │   │
│  │   │ 提示  │    │ (流式SSE渲染)   │    │ (流式检测)   │     │   │
│  │   └──────┘    └────────────────┘    └──────┬───────┘     │   │
│  │       ↑                                     │             │   │
│  │       └─────────── 收集结果，循环 ←──────────┘             │   │
│  │                                                           │   │
│  │   终止条件：模型响应中不包含任何 tool_use 块               │   │
│  │   关键特性：单次 API 调用可返回多个 tool_use 块（顺序执行）│   │
│  │                                                           │   │
│  └───────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─ 工具系统（26+ 内建工具）────────────────────────────────┐   │
│  │  每个工具实现:                                             │   │
│  │  ├── Input Schema（Zod 校验）                             │   │
│  │  ├── Permission Check → allow | deny | ask                │   │
│  │  ├── Execution Logic                                      │   │
│  │  └── Terminal UI Renderer                                 │   │
│  │                                                           │   │
│  │  核心工具: Bash, Read, Write, Edit, Glob, Grep            │   │
│  │  元工具: Task（生成子 Agent）                              │   │
│  │  扩展: MCP Server 提供运行时动态工具                       │   │
│  └───────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─ 权限系统（5 级模式）───────────────────────────────────┐    │
│  │  Mode 1: 全部询问（最安全）                              │    │
│  │  Mode 2: 读操作自动，写操作询问                          │    │
│  │  Mode 3: 工作区写自动，系统写询问                        │    │
│  │  Mode 4: 大部分自动，高风险询问                          │    │
│  │  Mode 5: 全自动（YOLO 模式）                            │    │
│  └───────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─ 生命周期钩子（12 个事件）──────────────────────────────┐    │
│  │  会话级: SessionStart, SessionEnd                        │    │
│  │  轮次级: UserPromptSubmit, Stop, StopFailure, PreCompact │    │
│  │  工具级: PreToolUse, PostToolUse, PostToolUseFailure     │    │
│  │  权限级: PermissionRequest                               │    │
│  │  多Agent: SubagentStart, SubagentStop                    │    │
│  │  系统级: Notification, Setup                             │    │
│  │                                                          │    │
│  │  钩子类型: Shell 命令 / HTTP 端点 / LLM Prompt           │    │
│  │  控制机制: exit code 0=允许, 2=阻止                      │    │
│  └───────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─ 多 Agent 协调 ─────────────────────────────────────────┐    │
│  │  Subagents: Task 工具生成独立子 Agent                    │    │
│  │  ├── Explore 类型: 快速代码库导航                        │    │
│  │  ├── General 类型: 复杂推理                              │    │
│  │  └── 可选模型: haiku(快) / sonnet(均衡) / opus(强)       │    │
│  │                                                          │    │
│  │  Agent Teams (实验性): 多 Agent 对等协作                  │    │
│  │  ├── 直接 Agent 间消息传递                               │    │
│  │  ├── 共享任务列表                                        │    │
│  │  └── 适用于跨层协调（前端/后端/数据库）                   │    │
│  └───────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─ Agent SDK（编程接口）──────────────────────────────────┐    │
│  │  Python SDK + TypeScript SDK                             │    │
│  │  ├── 编程式控制工具、权限、成本限制、输出                 │    │
│  │  ├── 自定义 Agent 循环逻辑                               │    │
│  │  └── 嵌入到 CI/CD 管线                                   │    │
│  └───────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

#### Agent 循环的流式执行细节

```
用户输入
    │
    ▼
┌─ API 请求 ──────────────────────────────────────┐
│  system_prompt + tools + messages → Anthropic API │
└──────────────────────┬──────────────────────────┘
                       │
                       ▼ Server-Sent Events (流式)
┌─ 流式响应处理 ────────────────────────────────────┐
│                                                    │
│  ├── 文本块 → 增量渲染到终端                        │
│  ├── tool_use 块检测（流式中途识别）                 │
│  │     ↓                                           │
│  │   ┌─ 工具执行管线 ──────────────────┐            │
│  │   │  1. PreToolUse 钩子 → 可阻止     │            │
│  │   │  2. Permission Check             │            │
│  │   │     ├── allow → 直接执行          │            │
│  │   │     ├── deny → 返回拒绝消息       │            │
│  │   │     └── ask → 向用户请求审批      │            │
│  │   │  3. 执行工具逻辑                  │            │
│  │   │  4. PostToolUse 钩子              │            │
│  │   │  5. 收集 tool_result              │            │
│  │   └──────────────────────────────────┘            │
│  │                                                    │
│  └── 响应完成                                         │
│       ├── 包含 tool_use → 将 tool_result 追加，循环    │
│       └── 不含 tool_use → 终止循环，输出最终响应        │
│                                                       │
└───────────────────────────────────────────────────────┘
```

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 流式 Agent 循环响应性极佳 | 仅绑定 Anthropic 模型 |
| 12 个钩子覆盖完整生命周期 | 钩子系统复杂度高，调试困难 |
| 5 级权限精细可控 | 权限配置学习曲线陡峭 |
| Agent SDK 支持编程式嵌入 | SDK 仅支持 Python/TypeScript |
| 子 Agent + Agent Teams 双模式 | Agent Teams 仍为实验性 |
| MCP 动态工具扩展 | MCP 工具的权限管理额外复杂 |

#### 优缺点

| 优点 | 缺点 |

### 3.3 OpenAI Codex CLI

#### Harness 架构总览

Codex CLI 的 Harness 基于 **App Server（双向 JSON-RPC）** 架构，将 Agent 引擎与多客户端表面解耦：

```
┌─────────────────────────────────────────────────────────────────┐
│                Codex CLI Harness 全景图                          │
│                                                                 │
│  ┌─ 客户端表面（多入口）───────────────────────────────────┐    │
│  │  CLI          VS Code Extension    Web App    Desktop App │   │
│  │    ↕              ↕                 ↕            ↕        │   │
│  │  ┌──────────────────────────────────────────────────┐     │   │
│  │  │         JSON-RPC 2.0 协议层                       │     │   │
```

#### App Server 的设计决策

值得注意的是，OpenAI **拒绝了 MCP（Model Context Protocol）**，选择自建 JSON-RPC 协议，原因是 MCP 难以维护 IDE 使用场景中的语义一致性。

```
为什么自建协议而非使用 MCP:

MCP 的局限:
├── 面向通用工具通信设计
├── 不支持 IDE 特有语义（Diff、审批流、流式渲染）
├── 缺少双向通信能力（Agent 主动向客户端请求审批）
└── 对话状态管理不在协议范围内

Codex App Server 的优势:
├── 双向 JSON-RPC：Agent 可主动请求人类审批
├── 原生支持 Thread/Turn/Item 三层抽象
├── Diff-based 代码变更（非全量重写）
├── 流式进度更新
└── 统一多客户端体验（CLI/IDE/Web/Desktop）
```

#### 优缺点

| 优点 | 缺点 |
|------|------|
| App Server 架构解耦引擎与客户端 | 自建协议，生态兼容性差（非 MCP） |
| 双层安全控制（沙箱+审批）最精细 | 仅绑定 OpenAI 模型 |
| Thread 支持恢复/分叉/归档 | 架构复杂度高 |
| 多客户端共享同一 Agent 引擎 | 闭源 App Server 核心 |
| 审批策略渐进式自动化 | 网络访问默认禁用，配置繁琐 |

```

        "tool": "shell",
        "args_pattern": "rm -rf *"
      },
      "decision": "deny",
      "priority": 100,
      "reason": "禁止递归删除"
    },
    {
      "condition": {
        "tool": "file_write",
        "args_pattern": "*.env"
      },
      "decision": "ask_user",
      "priority": 90,
      "reason": "写入环境配置需确认"
    },
    {
      "condition": {
        "tool": "file_read"
      },
      "decision": "allow",
      "priority": 1,
      "reason": "读操作默认允许"
    }
  ]
}

规则评估流程:
1. 收集所有匹配当前工具调用的规则
2. 按 priority 降序排序
3. 取最高优先级规则的 decision
4. 执行对应操作（allow/deny/ask_user）
```

### 5.2 错误恢复与自愈模式

#### 三类 AI 特有失败模式

```
┌─────────────────────────────────────────────────────────────────┐
│              AI Agent 三类特有失败模式                            │
│                                                                 │
│  ┌─ The Repeater（重复者）──────────────────────────────────┐   │
│  │  症状: 反复执行相同的工具调用，状态不变                    │   │
│  │  例子: 连续读取同一文件 5 次                              │   │
│  │  检测: 最近 N 次操作的哈希值完全相同                      │   │
│  │  恢复: 注入"你正在重复操作"提示 + 建议替代方案            │   │
│  └───────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─ The Wanderer（漫游者）──────────────────────────────────┐   │
│  │  症状: 活跃但偏离原始目标                                 │   │
│  │  例子: 被要求修 bug，却开始重构整个模块                   │   │
│  │  检测: 进度指标长时间未变化 + 操作与原始目标相关性下降     │   │
│  │  恢复: 注入"请回到原始任务"提示 + 重申目标                │   │
│  └───────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─ The Looper（循环者）────────────────────────────────────┐   │
│  │  症状: 在固定的操作集合间交替，无法跳出                   │   │
│  │  例子: 修改 → 测试失败 → 撤销 → 修改 → 测试失败...       │   │
│  │  检测: 最近操作形成固定模式（周期检测算法）               │   │
│  │  恢复: 中断循环 + 提供失败历史 + 建议完全不同的方案       │   │
│  └───────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

```
│                          ↓                                   │
│  ┌─ 4. Escalate（升级）──────────────────────────────────┐   │

│  │  Tier 3 失败: 人类升级                                  │   │
```

```
│  │  └── 致命故障 → Circuit Breaker（连续 3 次失败断路）     │     │
│  │                                                         │     │
│  │  参考: 自愈管线 + 上下文注入式恢复                       │     │
│  └─────────────────────────────────────────────────────────┘     │
│                                                                 │
│  ┌─ Layer 6: 验证闭环 ────────────────────────────────────┐     │
│  │                                                         │     │
│  │  Build → Verify → Self-Fix 循环:                        │     │
│  │  ├── 修改代码后自动运行:                                 │     │
│  │  │   ├── 类型检查                                       │     │
│  │  │   ├── Linter                                         │     │
│  │  │   ├── 构建                                           │     │
│  │  │   └── 测试                                           │     │
│  │  ├── 全部通过 → 完成                                    │     │
│  │  └── 有失败 → 注入结构化错误上下文 → 重试（最多 3 次）  │     │
│  │                                                         │     │
│  │  参考: Gemini CLI Plan→Act→Validate                     │     │
│  └─────────────────────────────────────────────────────────┘     │
│                                                                 │
│  ┌─ Layer 7: 生命周期钩子 ────────────────────────────────┐     │
│  │                                                         │     │
│  │  最小可用钩子集合（8 个）:                                │     │
│  │  ├── SessionStart / SessionEnd                           │     │
│  │  ├── UserSubmit / AgentResponse                          │     │
│  │  ├── PreToolUse / PostToolUse                            │     │
│  │  ├── PreCompact                                          │     │
│  │  └── Error                                               │     │
│  │                                                         │     │
│  │  钩子类型: Shell 命令 / HTTP 端点                        │     │
│  │  控制: exit code 0=允许, 2=阻止, 其他=警告               │     │
│  │                                                         │     │
│  │  参考: Claude Code 12 事件（按需渐进式扩展）             │     │
│  └─────────────────────────────────────────────────────────┘     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 7.2 核心接口设计

```typescript
// Agent 循环引擎
interface AgentLoop {
  run(input: UserInput): AsyncGenerator<StreamEvent>;
  interrupt(): void;
  resume(checkpoint: Checkpoint): AsyncGenerator<StreamEvent>;
}

// 流式事件类型
type StreamEvent =
  | { type: 'text'; content: string }
  | { type: 'tool_call'; tool: string; input: any }
  | { type: 'tool_result'; tool: string; output: any }
  | { type: 'approval_request'; tool: string; reason: string }
  | { type: 'error'; error: AgentError }
  | { type: 'done'; summary: string };

// 工具注册器
interface ToolRegistry {
  register(tool: Tool): void;
  registerMCP(server: MCPServer): Promise<void>;
  get(name: string): Tool | undefined;
  list(): ToolDescriptor[];
  healthCheck(): Promise<Map<string, boolean>>;
}

// 权限策略引擎
interface PolicyEngine {
  addRule(rule: PolicyRule): void;
  evaluate(toolCall: ToolCall, ctx: Context): Decision;
  recordApproval(toolCall: ToolCall, scope: 'once'|'session'|'persist'): void;
}

interface PolicyRule {
  condition: {
    tool?: string | RegExp;
    argsPattern?: Record<string, any>;
    environment?: string;
  };
  decision: 'allow' | 'deny' | 'ask_user';
  priority: number;
  reason?: string;
}

// 多 Agent 协调器
interface AgentCoordinator {
  spawnWorker(task: TaskDescription, config: WorkerConfig): Promise<WorkerHandle>;
  awaitWorker(handle: WorkerHandle): Promise<WorkerResult>;
  broadcastToWorkers(message: CoordinationMessage): void;
  getWorkerStatus(handle: WorkerHandle): WorkerStatus;
}

interface WorkerConfig {
  model: string;
  maxTokens: number;
  timeout: number;
  tools: string[];            // 允许的工具子集
  depthLimit: number;         // 递归深度限制
  isolateContext: boolean;    // 是否隔离上下文
}

// 错误恢复器
interface ErrorRecovery {
  detect(history: ActionHistory): FailureMode | null;
  classify(error: AgentError): ErrorCategory;
  recover(failure: ClassifiedFailure): RecoveryAction;
  circuitBreaker: CircuitBreaker;
}

type FailureMode = 'repeater' | 'wanderer' | 'looper';
type ErrorCategory = 'transient' | 'context_overflow' | 'output_malformed'
                   | 'logic_failure' | 'downstream_failure' | 'fatal';

// 验证闭环
interface VerificationLoop {
  verify(changes: FileChange[]): Promise<VerificationResult>;
  selfFix(failures: VerificationFailure[], maxRetries: number): Promise<boolean>;
}

interface VerificationResult {
  passed: boolean;
  checks: {
    typeCheck: CheckResult;
    lint: CheckResult;
    build: CheckResult;
    test: CheckResult;
  };
  failures: VerificationFailure[];
}

// 生命周期钩子
interface HookSystem {
  on(event: HookEvent, handler: HookHandler): void;
  off(event: HookEvent, handler: HookHandler): void;
  emit(event: HookEvent, data: HookData): Promise<HookDecision>;
}

type HookEvent = 'SessionStart' | 'SessionEnd' | 'UserSubmit' | 'AgentResponse'
               | 'PreToolUse' | 'PostToolUse' | 'PreCompact' | 'Error';

type HookDecision = 'allow' | 'block' | 'modify';
```

### 7.3 实施路线图

```
Phase 1: 核心循环（第 1-2 周）
├── 实现流式 ReAct Loop（SSE 输出）
├── 实现基础工具系统（Read/Write/Bash/Grep/Glob）
├── 实现工具 Schema 校验（Zod/JSON Schema）
├── 实现基础权限检查（safe/medium/high 三级）
└── 端到端: 能完成简单单文件修改任务

Phase 2: 安全与权限（第 3-4 周）
├── 实现沙箱隔离（文件系统+网络+进程限制）
├── 实现 Policy Engine（规则+优先级+决策）
├── 实现审批工作流（accept-once/session/persist）
├── 实现基础生命周期钩子（8 个事件）
├── 安全测试: 验证安全红线不可突破
└── MCP 工具动态加载

Phase 3: 多 Agent + 错误恢复（第 5-6 周）
├── 实现 Controller-Worker 多 Agent 协调
├── 实现子 Agent 上下文隔离
├── 实现 StuckDetector（Repeater/Wanderer/Looper 检测）
├── 实现指数退避重试 + Circuit Breaker
├── 实现上下文注入式错误恢复
└── 故障注入测试

Phase 4: 验证闭环 + 优化（第 7-8 周）
├── 实现 Build → Verify → Self-Fix 循环
├── 集成类型检查/Linter/构建/测试 自动化验证
├── 实现会话管理（持久化/恢复/分叉）
├── SWE-bench Verified 基准测试
├── 可观测性: 上下文组成追踪 + 工具调用链
└── 性能优化: Prompt Caching + 工具并行执行
```

### 7.4 关键设计原则总结

| 原则 | 说明 | 参考来源 |
|------|------|---------|
| **安全是不可协商的基线** | 沙箱+策略引擎双层控制，安全红线不可被模型绕过 | Codex CLI 双层安全 |
| **引擎与表面解耦** | Agent 循环引擎独立于客户端（CLI/IDE/Web） | Codex App Server |
| **流式优先** | 所有 Agent 响应和工具执行都应该是流式的 | Claude Code SSE 流 |
| **验证驱动** | 每次代码修改后自动验证（类型+Lint+构建+测试） | Gemini CLI P→A→V |
| **隔离防污染** | 子 Agent 独立上下文，防止噪音传播到主 Agent | 所有主流 Agent |
| **渐进式自动化** | 从"全部询问"到"全自动"提供多级权限，用户可控 | Claude Code 5 级 |
| **失败即学习** | 每次错误都注入完整失败历史，避免重复犯错 | 上下文注入式恢复 |
| **钩子可扩展** | 所有关键决策点暴露钩子，允许外部逻辑介入 | Claude Code 12 钩子 |
