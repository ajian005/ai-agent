## 1. 什么是上下文工程

### 1.1 定义

**上下文工程（Context Engineering）** 是管理 AI Agent 整个信息环境的学科——决定模型**看到什么信息**、**在什么时机看到**、**以什么结构呈现**。

> "The delicate art and science of filling the context window with just the right information for the next step." —— Andrej Karpathy

### 1.2 上下文工程 vs 提示词工程

```
┌────────────────────────────────────────────────────────────────────┐
│                     上下文工程 vs 提示词工程                         │
├──────────────┬─────────────────────┬───────────────────────────────┤
│              │   提示词工程          │   上下文工程                   │
├──────────────┼─────────────────────┼───────────────────────────────┤
│ 关注点        │ 如何措辞指令         │ 管理所有进入上下文窗口的信息    │
│ 范围          │ System Prompt       │ System Prompt + 对话历史 +     │
│              │                     │ 工具结果 + 检索文档 + 状态     │
│ 类比          │ "告诉模型怎么说话"   │ "控制模型看到什么"              │
│ 失败原因      │ 措辞不当            │ 状态管理失控、信息过载或缺失    │
│ 适用阶段      │ 单轮问答            │ 多步骤Agent工作流               │
│ 核心技能      │ 语言技巧            │ 系统架构设计                   │
└──────────────┴─────────────────────┴───────────────────────────────┘
```

### 1.3 为什么上下文工程至关重要

研究表明：

- **上下文质量 > 模型能力**：在弱模型上使用干净、结构化的上下文，效果优于在强模型上使用混乱的上下文
- **聚焦的 20K token 上下文往往优于臃肿的 200K token 上下文**
- **65% 的企业 AI Agent 故障** 源于上下文漂移或记忆丢失，而非 token 不足
- 有效的上下文管理可以 **降低 60-80% 的 API 成本**

### 1.4 上下文窗口中都有什么

一个 AI Agent 的上下文窗口是由多种信息源组成的：

```
┌───────────────────────────────────────────────────────────────┐
│                    上下文窗口（200K tokens 示例）                │
│                                                               │
│  ┌─────────────────┐  系统提示词 ..................... ~5-30K  │
│  ├─────────────────┤  工具定义（JSON Schema）........... ~5-15K │
│  ├─────────────────┤  对话历史 ........................ ~20-80K │
│  ├─────────────────┤  工具调用结果（文件、搜索等）..... ~30-80K  │
│  ├─────────────────┤  检索的代码上下文 ............... ~10-30K  │
│  ├─────────────────┤  记忆/状态摘要 ................... ~2-5K  │
│  ├─────────────────┤  环境信息 ....................... ~1-2K   │
│  └─────────────────┘  预留输出空间 .................... ~8-16K  │
│                                                               │
│  实际可用于"思考"的空间 = 窗口大小 - 以上所有                     │
└───────────────────────────────────────────────────────────────┘
```

**关键洞察**：工具结果通常是上下文中增长最快、占比最大的部分（可达窗口的 50%），是上下文工程的首要管理对象。

## 2. 上下文工程的核心问题与失败模式

### 2.1 四大失败模式

```
┌─────────────────────────────────────────────────────────────────┐
│                      上下文失败模式                               │
├──────────────────┬──────────────────────────────────────────────┤
│ Context Poisoning │ 上下文投毒：模型的幻觉输出被保留在对话历史中，   │
│ 上下文投毒        │ 后续步骤将其当作事实引用，导致错误级联传播       │
├──────────────────┼──────────────────────────────────────────────┤
│ Context Distraction│上下文干扰：累积的工具结果、无关文件内容等       │
│ 上下文干扰       │ 信息量过大，淹没了真正重要的指令和上下文         │
├──────────────────┼──────────────────────────────────────────────┤
│ Context Confusion │ 上下文混淆：无关信息影响决策，例如读取了错误的    │
│ 上下文混淆       │ 文件、引入了与当前任务无关的代码上下文           │
├──────────────────┼──────────────────────────────────────────────┤
│ Context Clash     │ 上下文冲突：来自不同来源的信息互相矛盾，例如     │
│ 上下文冲突       │ 记忆文件说"用 v2 API"而检索到的代码用"v1 API"   │
└──────────────────┴──────────────────────────────────────────────┘
```

### 2.2 上下文腐蚀（Context Rot）

上下文腐蚀是 AI Agent 随时间推移性能退化的核心原因：

```
准确率
  ↑
100%│ ████
    │ ████ ██
    │ ████ ████
 80%│ ████ ████ ██
    │ ████ ████ ████
    │ ████ ████ ████ ██
 60%│ ████ ████ ████ ████
    │ ████ ████ ████ ████ ██
    │ ████ ████ ████ ████ ████
 40%│ ████ ████ ████ ████ ████ ████
    │ ████ ████ ████ ████ ████ ████ ████
 20%│ ████ ████ ████ ████ ████ ████ ████ ████
    └──────────────────────────────────────────→ 上下文长度
     10K   20K   32K   64K  100K  128K  200K

• 每个 LLM 的准确率都随上下文增长而下降（测试 18 个模型，无一例外）
• 32K-64K tokens 区间常出现"性能悬崖"
• 根因：Transformer 自注意力的二次方缩放
  - 10K tokens → 1亿对关系
  - 100K tokens → 100亿对关系 → 注意力精度退化
```

### 2.3 上下文工程的核心挑战

| 挑战 | 说明 | 典型场景 |
|------|------|---------|
| **Token 预算有限** | 所有信息共争一个窗口 | 30K 系统提示词 + 50K 工具结果 = 仅剩 120K 给其他 |
| **工具结果膨胀** | 30 分钟工作后工具结果可占窗口 50% | 读了 20 个文件、执行了 15 条命令 |
| **中间遗忘效应** | 窗口中间部分的信息被模型忽略 | 关键指令放在中间段落 |
| **跨会话记忆** | 新会话丢失之前的所有决策和发现 | 次日恢复工作时重复相同的错误 |
| **信息新鲜度** | 旧信息可能已过时但仍在上下文中 | 文件已修改但旧版本仍在对话历史 |

## 3. 各 Agent 上下文工程详细分析

### 3.1 Claude Code

#### 上下文架构总览

Claude Code 拥有业界最复杂的上下文工程系统，采用 **三层压缩 + 五层记忆** 的架构：

```
┌─────────────────────────────────────────────────────────────┐
│                 Claude Code 上下文全景图                      │
│                                                             │
│  ┌─ 上下文窗口（~200K tokens）────────────────────────┐      │
│  │                                                    │      │
│  │  系统提示词（6层优先级，cache boundary 分离）         │      │
│  │       ↕ 缓存边界                                   │      │
│  │  动态上下文（环境 + 记忆 + MCP）                     │      │
│  │  工具定义（40+ 工具的 JSON Schema）                  │      │
│  │  对话历史（经过 MicroCompaction 清理）               │      │
│  │  ★ 工具结果（Hot Tail 保留 / Cold Storage 卸载）    │      │
│  │  预留空间（输出 + 压缩操作用）                       │      │
│  └────────────────────────────────────────────────────┘      │
│                                                             │
│  ┌─ 外部存储 ─────────────────────────────────────────┐      │
│  │  CLAUDE.md 文件（项目/目录/全局三级）                │      │
│  │  Scratchpad 目录（临时工作笔记）                    │      │
│  │  Auto-memory 目录（自动提取的记忆）                  │      │
│  │  会话 Transcript（原始对话记录）                     │      │
│  └────────────────────────────────────────────────────┘      │
└─────────────────────────────────────────────────────────────┘
```

#### 三层压缩系统（核心创新）

Claude Code 的三层压缩系统是其上下文工程的最大亮点：

**Tier 1: MicroCompaction（微压缩）——工具结果清理**

```
触发时机：每轮对话后自动执行
目标对象：旧的工具调用结果（Read、Bash、Grep、Glob、WebSearch 等）
实现方式：非 LLM 驱动，纯策略性清理

┌─ 对话历史中的工具结果 ──────────────────────────┐
│                                                 │
│  Turn 1: Read(auth.py)    → 卸载到磁盘 (Cold)   │
│  Turn 2: Bash(npm test)   → 卸载到磁盘 (Cold)   │
│  Turn 3: Grep(TODO)       → 卸载到磁盘 (Cold)   │
│  Turn 4: Read(config.ts)  → 保留在上下文 (Hot)   │  ← Hot Tail
│  Turn 5: Bash(npm build)  → 保留在上下文 (Hot)   │  ← Hot Tail
│                                                 │
│  Cold Storage: 保存到磁盘，保留调用记录（无内容） │
│  Hot Tail: 最近 N 个结果完整保留供推理使用       │
└─────────────────────────────────────────────────┘

两种执行路径：
├── 时间驱动清除：服务器缓存过期后直接修改消息内容
└── 缓存感知微压缩：利用 cache_edits API 块保持缓存命中
```

**Tier 2: Session Memory（会话记忆）——结构化替换**

```
触发时机：自动压缩阈值（可用空间 < 预留空间时）
实现方式：非 LLM 驱动，用预构建记忆替换旧消息
压缩率：60-80% token 压缩
优势：无需 LLM 调用，零额外成本

┌─ 压缩前 ──────────────┐    ┌─ 压缩后 ──────────────┐
│ 50K tokens 对话历史     │ → │ 10K tokens 结构化摘要   │
│ （含大量工具结果）       │    │ + 最近 N 轮完整对话    │
└────────────────────────┘    └────────────────────────┘
```

**Tier 3: Full Compaction（完整压缩）——LLM 驱动摘要**

```
触发时机：上下文接近容量上限 或 用户执行 /compact 命令
实现方式：LLM 驱动的智能摘要
输出结构：9 段结构化摘要

┌─ 压缩摘要结构 ─────────────────────────────┐
│  1. 用户意图（当前任务目标）                  │
│  2. 技术概念（涉及的技术栈和模式）            │
│  3. 已触及文件（修改/读取的文件列表）          │
│  4. 遇到的错误（及其解决方案）               │
│  5. 用户消息重点（关键需求和偏好）            │
│  6. 待处理任务（尚未完成的工作）              │
│  7. 当前工作状态（正在进行的操作）            │
│  8. [链式思维推理 → 压缩后剥离]              │
│  9. 恢复指令（重新水合最近文件和 TODO）       │
└────────────────────────────────────────────┘

关键优化：压缩调用复用主对话的系统提示词和缓存 key，
         实现缓存命中而非 98% 缓存未命中
```

#### 五层记忆系统

```
┌─ 记忆层级 ─────────────────────────────────────────────┐
│                                                         │
│  Layer 1: 上下文窗口内记忆                               │
│  └── 当前对话中的信息（由三层压缩管理）                    │
│                                                         │
│  Layer 2: CLAUDE.md 配置记忆                             │
│  └── 项目级 / 目录级 / 全局级指令和偏好                   │
│                                                         │
│  Layer 3: Scratchpad 工作记忆                            │
│  └── 临时工作笔记，当前任务的中间状态                      │
│                                                         │
│  Layer 4: Auto-memory 提取记忆                           │
│  └── 后台 Agent 自动从对话中提取持久化信息                 │
│                                                         │
│  Layer 5: Session Transcript 原始记录                    │
│  └── 完整对话原始记录，支持跨会话审计和恢复                │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

#### Prompt Caching 策略

```
API 调用结构:
{
  "system": [
    {
      "text": "[静态系统提示词 ~20K tokens]",
      "cache_control": { "type": "ephemeral" }   ← 缓存标记
    },
    {
      "text": "[动态上下文 ~5K tokens]"            ← 每次变化，不缓存
    }
  ],
  "messages": [...]
}

效果：
├── 首次请求：写入缓存，正常计费
├── 后续请求：缓存命中，成本降 ~90%，延迟降 ~85%
└── 缓存 key：基于静态部分内容哈希
```

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 三层压缩覆盖所有场景 | 架构极其复杂，调试困难 |
| MicroCompaction 零 LLM 成本 | 仅适配 Anthropic API（cache_edits 等） |
| 五层记忆实现跨会话连续性 | 压缩后仍可能丢失关键信息 |
| 缓存策略极大降低成本 | 30K token 系统提示词本身占用过大 |
| 9 段结构化摘要保留关键信息 | 依赖启发式规则（Hot Tail 大小等） |

### 3.2 Cursor

#### 上下文架构总览

Cursor 的核心竞争力在于 **IDE 深度集成的上下文感知** 和 **语义化代码检索**：

```
┌─────────────────────────────────────────────────────────────┐
│                  Cursor 上下文全景图                          │
│                                                             │
│  ┌─ 代码库索引层 ────────────────────────────────────┐       │
│  │  Tree-sitter AST 解析 → 语义代码块提取             │       │
│  │  向量嵌入 → Turbopuffer 向量数据库                  │       │
│  │  Merkle Tree → 增量重索引                          │       │
│  │  依赖图 → 导入/调用关系追踪                        │       │
│  └──────────────────────────────────────────────────┘       │
│                         ↓ 检索                              │
│  ┌─ 上下文编排层 ────────────────────────────────────┐       │
│  │                                                   │       │
│  │  Phase 1: IDE 状态收集                            │       │
│  │  ├── 当前打开的文件和光标位置                       │       │
│  │  ├── 最近编辑的文件（带修改 diff）                  │       │
│  │  ├── 活跃的 Linter 错误                           │       │
│  │  └── 终端输出                                     │       │
│  │                                                   │       │
│  │  Phase 2: 语义检索                                │       │
│  │  ├── 查询向量化 → ANN 搜索                        │       │
│  │  ├── 依赖图遍历 → 调用者/被调用者                  │       │
│  │  └── BM25 关键词搜索（混合检索）                   │       │
│  │                                                   │       │
│  │  Phase 3: 重排序与预算分配                         │       │
│  │  ├── 新近度加权（最近编辑的文件优先）               │       │
│  │  ├── 调用深度加权（近依赖优先）                    │       │
│  │  └── Token 预算裁剪                               │       │
│  │                                                   │       │
│  └──────────────────────────────────────────────────┘       │
│                         ↓                                   │
│  ┌─ 上下文窗口 ─────────────────────────────────────┐       │
│  │  系统提示词（7 段结构）                            │       │
│  │  精选的代码上下文                                  │       │
│  │  IDE 状态信息                                     │       │
│  │  对话历史                                         │       │
│  │  用户消息                                         │       │
│  └──────────────────────────────────────────────────┘       │
└─────────────────────────────────────────────────────────────┘
```

#### 代码库索引系统（RAG Pipeline）

**Step 1: 语义解析**
```
源代码文件
    ↓ Tree-sitter 解析
抽象语法树 (AST)
    ↓ 语义单元提取
┌──────────────────────────────┐
│ 语义代码块:                   │
│  ├── function authenticate() │ ← 完整函数体
│  ├── class UserService       │ ← 完整类定义
│  ├── interface Config        │ ← 完整接口
│  └── module.exports = {...}  │ ← 完整导出块
│                              │
│ 每个块包含元数据:              │
│  ├── 文件路径                 │
│  ├── 行号范围                 │
│  ├── 符号名称                 │
│  └── 类型（函数/类/方法...）   │
└──────────────────────────────┘

优势：不会在函数中间截断，保证代码块语义完整性
```

**Step 2: 向量嵌入与存储**
```
语义代码块 → Embedding Model → 向量表示
                                   ↓
                         Turbopuffer 向量数据库
                         ├── 支持百万级代码块
                         ├── 近实时搜索
                         └── 支持元数据过滤
```

**Step 3: 混合检索**
```
用户查询
    ↓
┌──────────────────┬───────────────────┐
│  语义搜索         │  关键词搜索        │
│  (向量 ANN)       │  (BM25)           │
├──────────────────┼───────────────────┤
│  找"概念相似"的代码│  找"精确标识符"匹配 │
│  例如: "认证逻辑"  │  例如: "UserAuth"  │
│  → 找到 JWT,      │  → 精确找到类名     │
│    OAuth, 密码验证 │                   │
└──────────────────┴───────────────────┘
         ↓ 融合排序
    最终检索结果
```

**Step 4: 增量索引（Merkle Tree）**
```
完整代码库哈希树:
         root_hash
        /         \
    dir_hash_1   dir_hash_2
    /    \         /    \
  file_1 file_2  file_3 file_4

文件修改时 → 仅重新计算受影响的分支
索引复用 → 团队间 92% 相似代码库可共享索引
```

#### 上下文优先级策略（逆向工程发现）

通过黑盒测试揭示的 Cursor 上下文优先级：

```
优先级从高到低:

1. 光标局部上下文（当前文件、光标附近代码）    ★★★★★
   └── Cursor 极度优先光标附近的代码和注释

2. 最近编辑/打开的文件                        ★★★★
   └── 新近度 > 语义相关性（关键发现！）

3. 语义检索结果                               ★★★
   └── 跨仓库的语义搜索，但容易被近期上下文覆盖

4. 依赖图关联                                 ★★
   └── 导入/调用关系追踪到的相关代码

5. 全局代码库搜索                              ★
   └── 最广但优先级最低的搜索
```

#### Dynamic Context Discovery（2025-2026 演进）

```
传统方式:                        Dynamic Context Discovery:
┌──────────────┐               ┌──────────────────────────┐
│ 预加载大量上下文│               │ 初始提供最少上下文         │
│ 一次性塞入窗口 │               │     ↓                    │
│ 可能包含无关信息│               │ Agent 按需拉取相关上下文   │
│ 占用大量 token │               │     ↓                    │
└──────────────┘               │ 长响应 → 转为文件引用      │
                               │     ↓                    │
                               │ 压缩时引用对话历史保留关键点│
                               └──────────────────────────┘

核心理念: 少即是多——让 Agent 自己决定需要什么上下文
```

#### 优缺点

| 优点 | 缺点 |
|------|------|
| Tree-sitter AST 保证代码块语义完整 | 闭源，无法直接审查索引质量 |
| 混合检索（向量+BM25）兼顾语义和精确搜索 | 新近度过度优先可能忽略更相关的旧代码 |
| Merkle Tree 增量索引极高效 | 依赖本地索引服务，大型仓库首次索引耗时 |
| IDE 深度集成提供丰富的隐式上下文 | 多模型切换时上下文策略无差异适配 |
| Dynamic Context Discovery 减少信息过载 | 上下文管理对用户不透明 |

Codex CLI 采用 **服务端压缩 + 客户端沙箱隔离** 的上下文管理方式：

```
┌─────────────────────────────────────────────────────────────┐
│                Codex CLI 上下文管理架构                       │
│                                                             │
│  ┌─ 客户端（CLI）────────────────────────────────────┐       │
│  │  用户输入 + 对话历史管理                            │       │
│  │  /compact 命令触发                                 │       │
│  │  沙箱策略执行（landlock 隔离）                      │       │
│  └──────────────────────────────────────────────────┘       │
│                    ↕ API 调用                               │
│  ┌─ 服务端 ─────────────────────────────────────────┐       │
│  │                                                   │       │
│  │  /responses 端点                                  │       │
│  │  ├── context_management: {                        │       │
│  │  │     compact_threshold: <token数>               │       │
│  │  │   }                                            │       │
│  │  ├── 自动压缩：超过阈值时服务端触发                  │       │
│  │  └── 返回加密 compaction item                     │       │
│  │                                                   │       │
│  │  /responses/compact 端点（独立压缩）               │       │
│  │  ├── 显式无状态压缩                                │       │
│  │  └── 返回压缩后的上下文窗口                         │       │
│  │                                                   │       │
│  └──────────────────────────────────────────────────┘       │
└─────────────────────────────────────────────────────────────┘
```

#### 服务端压缩机制

```
请求流程:

1. 客户端发送完整对话历史到 /responses 端点
2. 服务端计算当前 token 数
3. 如果超过 compact_threshold:
   ├── 自动执行服务端压缩
   ├── 生成加密的 compaction item（携带关键状态和推理）
   └── 返回 compaction item 给客户端
4. 客户端将 compaction item 作为下次请求的前缀

优势：加密 compaction item 可以携带比明文更多的信息（服务端解密）
```

#### Pre-Turn Auto-Compaction（2026 改进）

```
传统流程:                         Pre-Turn 压缩:
┌──────────────┐               ┌──────────────────────────┐
│ 用户发消息     │               │ 用户发消息                │
│ → 检查token数 │               │ → 将新消息与历史一起评估   │
│ → 超限则压缩   │               │ → 压缩时包含新消息上下文   │
│ → 再处理用户消息│               │ → 压缩结果包含最新意图     │
│ （两步串行）    │               │ → 直接处理（一步完成）     │
└──────────────┘               └──────────────────────────┘

改进点:
├── 压缩时纳入当前轮的用户输入，避免丢失最新意图
├── 保护 tail trimming 逻辑，防止过度裁剪
├── /compact 命令支持 reseed 功能
└── 结构化保留用户消息在本地压缩历史中
```

#### Sub-Agent 上下文隔离

```
主 Agent 上下文窗口（协调器）:
├── 系统提示词
├── 用户请求
├── 任务分解计划
└── Sub-Agent 的摘要结果（而非完整输出）

Sub-Agent 1 上下文窗口（独立）:     Sub-Agent 2 上下文窗口（独立）:
├── 子任务描述                     ├── 子任务描述
├── 相关文件内容                    ├── 相关文件内容
└── 执行结果                       └── 执行结果

隔离优势：Sub-Agent 读取 50 个文件的内容不会出现在协调器的上下文中
```

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 服务端压缩，客户端零复杂度 | 依赖 OpenAI 服务端，不可自定义压缩策略 |
| 加密 compaction item 信息密度高 | compaction item 不透明，无法调试 |
| Pre-Turn 压缩保留最新意图 | 无内建代码索引/检索系统 |
| Sub-Agent 隔离防止上下文污染 | 无持久化跨会话记忆 |
| 提示词极简，预留最大上下文空间 | 过度依赖服务端智能 |

```
    │
    ▼

    ▼

    │
```

#### 过度检索 + 重排序策略

```
传统 Top-K 检索:               过度检索 + 重排序:
查询 → Top 10 结果             查询 → Top 30 结果 (3x)
                                      ↓
                               重排序评分:
                               ├── 语义相关性 (0.4)
                               ├── 新近度 (0.3)
                               ├── 记忆类型权重 (0.2)
                               └── 来源多样性 (0.1)
                                      ↓
                               裁剪 → Top 10 结果

优势：初始检索宽泛（高召回），重排序精准（高精度）
```

#### 优缺点

| 优点 | 缺点 |
|------|------|
| ContextEngine 插件化，完全可定制 | 架构复杂度极高 |

| 记忆有明确的类型和生命周期 | 部署成本 $3-15/天 |
| 语义搜索（BM25+向量）跨记忆检索 | 多层交互时行为难预测 |

## 5. 超长上下文处理：五大核心策略

### 策略一：分层压缩（Tiered Compaction）

以 Claude Code 的三层压缩为代表：

```
┌─────────────────────────────────────────────────────────────┐
│                    分层压缩策略                               │
│                                                             │
│  Tier 1: 工具结果清理（每轮自动，零 LLM 成本）               │
│  ├── 目标: 占窗口 ~50% 的工具结果                           │
│  ├── 方法: Hot Tail（保留最近 N 个）+ Cold Storage（卸载旧的）│
│  ├── 成本: 零（纯策略性操作）                                │
│  └── 效果: 持续释放 20-40% 窗口空间                          │
│                                                             │
│  Tier 2: 结构化替换（自动触发，零 LLM 成本）                  │
│  ├── 目标: 旧对话历史                                       │
│  ├── 方法: 用预构建记忆模板替换旧消息                         │
│  ├── 成本: 零（模板化操作）                                  │
│  └── 效果: 60-80% 压缩率                                    │
│                                                             │
│  Tier 3: LLM 智能摘要（接近极限时，有 LLM 成本）             │
│  ├── 目标: 全部对话历史                                     │
│  ├── 方法: 结构化 9 段摘要 + 恢复/重新水合                   │
│  ├── 成本: 一次 LLM 调用                                    │
│  └── 效果: 最大程度压缩，但可能丢失细节                      │
│                                                             │
│  关键设计: 从低成本到高成本渐进式触发                          │
└─────────────────────────────────────────────────────────────┘
```

**自研建议**：至少实现 Tier 1（工具结果清理），效果最显著且零成本。

### 策略二：语义检索替代全量加载（Semantic RAG）

以 Cursor 的代码索引为代表：

```
┌─────────────────────────────────────────────────────────────┐
│                  语义检索策略                                 │
│                                                             │
│  核心思路: 不把整个代码库塞进上下文，只检索相关的部分          │
│                                                             │
│  实现管线:                                                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐    │
│  │ 代码解析   │→│ 语义切块   │→│ 向量嵌入   │→│ 索引存储   │    │
│  │ Tree-sitter│ │ 函数/类级  │ │ Embedding │ │ 向量数据库 │    │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘    │
│                                                             │
│  查询时:                                                     │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐    │
│  │ 查询嵌入   │→│ 混合检索   │→│ 重排序     │→│ Token裁剪  │    │
│  │           │ │ ANN+BM25  │ │ 多因子加权  │ │ 按预算截断  │    │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘    │
│                                                             │
│  效果:                                                       │
│  ├── 100K 行代码库 → 仅检索 ~5-10K tokens 相关代码           │
│  ├── 保证代码块语义完整（不在函数中间截断）                    │
│  └── 混合检索兼顾语义理解和精确标识符匹配                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**自研建议**：Tree-sitter 语义切块 + 向量嵌入是最佳实践组合。

### 策略四：Prompt Caching（提示词缓存）

```
┌─────────────────────────────────────────────────────────────┐
│                  Prompt Caching 策略                         │
│                                                             │
│  原理: 系统提示词在多次请求中大部分不变，可缓存               │
│                                                             │
│  ┌─ 无缓存 ────────────────────────────────────┐            │
│  │  每次请求: 发送 30K tokens → 30K token 计费   │            │
│  │  10 次请求: 300K tokens 计费                  │            │
│  └──────────────────────────────────────────────┘            │
│                                                             │
│  ┌─ 有缓存 ────────────────────────────────────┐            │
│  │  首次请求: 发送 30K tokens → 写入缓存         │            │
│  │  后续请求: 缓存引用 + 5K 动态部分 → 5K 计费   │            │
│  │  10 次请求: 30K + 9×5K = 75K tokens 计费     │            │
│  │  节省: 75%                                    │            │
│  └──────────────────────────────────────────────┘            │
│                                                             │
│  实现要点:                                                    │
│  1. 严格分离静态段（可缓存）和动态段（每次变化）               │
│  2. 静态段放在前面，动态段追加在后面                           │
│  3. 保持静态段内容哈希稳定（任何字符变化都会破坏缓存）         │
│  4. 工具定义也应设计为可缓存的（变化频率低）                   │
│                                                             │
│  各 Provider 支持:                                            │
│  ├── Anthropic: cache_control ephemeral 标记                 │
│  ├── OpenAI: 服务端自动缓存（prefix matching）               │
│  └── Google: 内建于 Gemini API                               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**自研建议**：Prompt Caching 是 ROI 最高的优化，实施简单但效果显著。

### 策略五：外部记忆 + 按需加载（External Memory + JIT Loading）

```
┌─────────────────────────────────────────────────────────────┐
│              外部记忆 + 按需加载策略                           │
│                                                             │
│  核心思路: 预加载轻量摘要，按需拉取完整内容                    │
│                                                             │
│  ┌─ Always Loaded（始终加载，~2K tokens）───────┐            │
│  │  MEMORY.md 摘要                              │            │
│  │  项目配置指令                                 │            │
│  │  技能列表描述（轻量级，仅名称+一行说明）       │            │
│  └──────────────────────────────────────────────┘            │
│                                                             │
│  ┌─ On-Demand（按需加载）──────────────────────┐             │
│  │  完整技能文件内容    ← 仅在需要该技能时加载    │             │
│  │  代码文件内容        ← 仅在需要读取时加载      │             │
│  │  搜索结果            ← 仅在需要搜索时加载      │             │
│  │  长期记忆的详细条目   ← 仅在语义搜索命中时加载 │             │
│  └──────────────────────────────────────────────┘            │
│                                                             │
│  Claude Code 技能架构实例:                                    │
│  ├── 所有技能描述总共仅占上下文的 ~2%                         │
│  ├── 完整技能内容仅在调用时加载                               │
│  └── 效果: 52 个技能注册但几乎不占上下文                      │

│  预算分配参考:                                                │
│  ├── 系统提示词: 5-15%                                       │

│  └── 输出预留: 5-10%                                         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**自研建议**：采用 "轻量索引 + 按需加载" 模式，技能/文件/记忆都只预加载描述。

### 6.4 信息新鲜度管理

```
问题: 文件在第 5 轮被读取，到第 20 轮时文件可能已修改
      但上下文中仍是第 5 轮的旧版本

解决方案:

1. 标记时间戳
   每个工具结果附带时间戳，模型可判断信息新鲜度

2. 重新验证
   修改文件后，自动在上下文中标注"此文件已被修改"
   或自动重新读取最新版本

3. Cursor 方式
   IDE 监听文件变化 → 更新索引 → 下次检索时自动返回最新版本

4. 冲突标记
   当检测到上下文中的信息与当前文件状态不一致时
   在上下文中显式标注冲突
```

| 维度 | 定义 | 测量方法 | 目标 |
|------|------|---------|------|
| **正确性** | 上下文中的信息是否准确、最新 | 人工审查 + 与源文件对比 | >95% |
| **完整性** | 是否包含了完成任务所需的所有信息 | 任务完成率对比（有/无特定上下文） | >90% |
| **相关性** | 上下文中的信息有多少与当前任务相关 | 相关信息占比 = 相关 tokens / 总上下文 tokens | >70% |
| **简洁性** | 是否用最少的 token 传达了必要信息 | token 效率 = 任务完成质量 / 使用的 token 数 | 持续优化 |
| **新鲜度** | 上下文中的信息是否反映最新状态 | 过时信息占比 | <5% |

### 8.2 关键设计原则

| 原则 | 说明 | 参考来源 |
|------|------|---------|
| **Token 即货币** | 每个进入上下文的 token 都有成本，必须证明其价值 | Context Budget Allocation |
| **渐进式披露** | 预加载轻量描述，按需加载完整内容 | Claude Code Skills / Cursor Dynamic Discovery |
| **新近度优先** | 最近的信息通常最重要，但不能完全压制语义相关性 | Cursor 上下文优先级 |
| **可观测优先** | 先建设上下文组成的可观测性，再基于数据优化 | 全部 Agent |
| **零成本压缩优先** | 先用不需要 LLM 调用的策略（工具结果清理），再用 LLM 摘要 | Claude Code MicroCompaction |
| **隔离防污染** | 复杂任务用 Sub-Agent 隔离，防止一个子任务污染全局上下文 | Codex CLI / OpenClaw |
| **记忆分层** | 不同生命周期的记忆用不同机制管理 | OpenClaw 四层记忆 |
| **缓存友好** | 设计静态/动态分离以最大化 Prompt Caching 效果 | Claude Code Cache Boundary |

### 8.3 实施路线图

```
Phase 1: 基础设施（第 1-2 周）
├── 实现 Token 预算管理器（记录每次请求的上下文分布）
├── 实现 Tier 1 工具结果清理（Hot Tail + Cold Storage）
├── 实现 Prompt Caching（静态/动态分离）
└── 建立上下文可观测性（记录 token 分布日志）

Phase 2: 代码检索（第 3-4 周）
├── 集成 Tree-sitter 进行 AST 解析
├── 实现语义代码块向量嵌入
├── 实现 BM25 + 向量混合检索
├── 实现增量索引（文件变更监听）
└── 建立检索质量评测（ContextBench 子集）

Phase 3: 压缩系统（第 5-6 周）
├── 实现 Tier 2 自动压缩（8 段结构化摘要模板）
├── 实现"记忆转移"压缩哲学（而非简单摘要）
├── 实现 /compact 手动压缩命令
├── 建立压缩保真度测试
└── 建立上下文腐蚀测试

Phase 4: 记忆系统（第 7-8 周）
├── 实现 MEMORY.md 持久化记忆
├── 实现跨会话记忆检索（语义搜索）
├── 实现 Sub-Agent 上下文隔离
├── 端到端评测（成本 + 质量 + 效率 + 稳定性）
└── 基于评测结果进行迭代优化
```

### 8.4 核心代码架构参考

```typescript
// 上下文管理器接口设计（参考 OpenClaw ContextEngine）
interface ContextManager {
  // 初始化：加载持久化记忆和项目配置
  bootstrap(config: ProjectConfig): Promise<void>;
  
  // 存储：记录新消息和工具结果
  ingest(message: Message | ToolResult): void;
  
  // 组装：为下一次模型调用构建完整上下文
  assemble(query: string, budget: TokenBudget): Promise<Context>;
  
  // 压缩：处理 token 超限
  compact(strategy: 'micro' | 'auto' | 'full'): Promise<void>;
  
  // 持久化：保存关键信息到外部存储
  persist(memory: MemoryEntry): Promise<void>;
  
  // 检索：从外部记忆检索相关信息
  recall(query: string, limit: number): Promise<MemoryEntry[]>;
}

// Token 预算分配
interface TokenBudget {
  total: number;              // 总窗口大小
  systemPrompt: number;       // 系统提示词预算
  tools: number;              // 工具定义预算
  memory: number;             // 常驻记忆预算
  history: number;            // 对话历史预算
  toolResults: number;        // 工具结果预算
  retrieval: number;          // 检索代码预算
  outputReserve: number;      // 输出预留
  compactionReserve: number;  // 压缩操作预留
}

// 工具结果管理（参考 Claude Code MicroCompaction）
interface ToolResultManager {
  hotTailSize: number;        // 保留最近 N 个结果
  maxResultSize: number;      // 单个结果最大 token 数
  offloadThreshold: number;   // 超过此大小卸载到文件
  
  add(result: ToolResult): void;
  getHotResults(): ToolResult[];       // 获取活跃结果
  getColdReferences(): Reference[];    // 获取已卸载结果的引用
  cleanup(): void;                     // 清理过期结果
}

// 压缩摘要模板（参考 OpenCode 8 段模板）
interface CompactionTemplate {
  sections: [
    'work_overview',           // 工作概述
    'user_directives',         // 用户指令（逐字保留）
    'failed_approaches',       // 已失败的方法
    'resolved_code',           // 已解决的代码与发现
    'how_things_work_now',     // 当前系统状态
    'credentials_config',      // 凭证和配置（逐字保留）
    'pending_tasks',           // 待处理任务
    'current_work'             // 当前进行的工作
  ];
  preserveRules: string[];     // 强制保留规则
}
```
